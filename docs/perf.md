## 1. 指标总表

**同一台机器、同一份产物、同一条命令，连续跑了 4 次**，表里给的是这 4 次的范围
（原始记录见 §2）。取区间而不是单值，是因为实测方差**很大** —— 见 §2.1。

| 指标 | 目标 | 实测（4 次采样） | 判定 |
| --- | --- | --- | --- |
| 冷启动到首帧可交互 | < 1200 ms | **316 – 935 ms** | ✅ 最坏值达标，余量 22% |
| 主进程常驻内存 | < 150 MB | **138.3 – 144.4 MB** | ⚠️ 最坏值达标，余量 **3.7%** |
| 渲染进程内存 | < 250 MB | **39.6 – 40.9 MB** | ✅ 余量 84% |
| 流式首 token 延迟 | < 300 ms（不含上游） | **27 – 28 ms** | ✅ 余量 91% |
| 流式帧率 | ≥ 55 fps | **179 – 180 fps** | ✅ 见 §2.5 的解释边界 |
| Win 安装包体积 | < 100 MB | **98.1 MB** | ⚠️ 达标，余量仅 **1.9%** |

目标值定义在 `packages/contract/src/perf.ts` 的 `PERF_TARGETS`，
判定函数是同文件的 `meetsTarget()` —— **`streamFps` 是唯一"越大越好"的指标**，
其余五项都是"越小越好"。两者共用一张表，所以比较方向写在函数里而不是散在调用点。

**六项都有实测值**。判定一律按**最坏值**取，不按最好值 —— 两项虽然达标但贴近上限，
改进项见 §3。

## 2. 每一项是怎么量出来的

性能报告最容易变成"看起来有人做过"的装饰品，所以这里逐项写清采集点 ——
每一个数字都能被追到一个具体的 `Date.now()` 或 `process.memoryUsage()`。

### 2.0 四次采样的原始值

| # | 时刻（UTC） | 冷启动 | main RSS | renderer RSS | 帧率 | 首 token |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 03:40:46 | **935 ms** | 144.44 MB | 39.60 MB | 180 fps | 28 ms |
| 2 | 03:53:46 | 361 ms | 139.2 MB | 40.1 MB | 180 fps | — |
| 3 | ~03:54 | 316 ms | 138.3 MB | 40.9 MB | 179 fps | — |
| 4 | 03:54:08 | 322 ms | 141.6 MB | 40.8 MB | 179 fps | 27 ms |

采样之间没有任何代码变更，只有间隔几分钟。`—` 表示那两次没有单独记录该值
（不是"没测到"）：帧率与首 token 每次都测了，只是第 2、3 次我只读了列表里的四项。

### 2.1 冷启动到首帧可交互 —— 316 ~ 935 ms

链路是**两段拼接**，因为没有任何一个进程同时看得见起点和终点：

```text
main: packages/shell-electron/src/main/perf.ts 模块顶层  ← Date.now() 记为 BOOT_AT
   │
   │  Electron 引导 → 建窗 → 加载 app:// → 渲染层挂载
   ▼
renderer: 双层 requestAnimationFrame 之后 samplePerf({ firstPaint: true })
   │
   ▼
main: firstPaintAt - BOOT_AT
```

三个刻意的选择：

- **起点放在模块顶层，不是 `app.whenReady()`**。模块顶层比 `whenReady` 早了整个
  Electron 引导阶段 —— 而那正是用户真实等待的时间。从 `whenReady` 起算会得到一个
  好看但没有意义的数字。
- **终点是双层 rAF，不是 `useEffect` 返回**。`useEffect` 只说明 DOM 节点建好了，
  第一帧还没上屏。连续两帧才是"画出来了"。
- **两侧都用挂钟时间（`Date.now()`），不用 `performance.now()`**。
  两个进程的 `performance.now()` 各自以自身启动为原点，加起来是错的。

> ### ⚠️ 这一项的方差是 2.9 倍，必须解释
>
> 第 1 次 935 ms，第 2–4 次 316 / 322 / 361 ms。代码没变、命令没变、机器没变。
>
> 最可能的解释是 **OS 页缓存**：`crossdeck.exe`（Electron 44 运行时主体，
> **234.6 MB**）在不在文件系统缓存里，直接决定它要被读多久。
> 第 1 次跑之前，这些文件已经很久没被访问；第 2 次起就在缓存里了。
> 量级也对得上：从磁盘读 200+ MB 与从缓存读，差的正是几百毫秒。
>
> **所以单独给一个"冷启动 XX ms"而不说明测量条件，这个数字的意义很有限。**
> 本表取**最坏值 935 ms** 作判定（它对应用户"装完之后第一次打开"的体验），
> 并在这里把区间写清楚 —— 复现的人跑出 320 ms 不应该以为自己测错了。
>
> 改进项见 §3.3：把测量条件固化下来，而不是靠读的人自行理解。

### 2.2 主进程常驻内存 —— 138.3 ~ 144.4 MB

`process.memoryUsage().rss`，在 main 进程原地读，无跨进程误差。
RSS 的口径是"进程整个驻留集"，包含 V8 堆、共享库映射与 Chromium 自身 ——
这正是任务管理器里会看到的那个数，因此比 `heapUsed` 更接近用户感受。

四次采样跨度 6.1 MB。判定取最坏值 144.44 MB（`151453696` 字节）。

### 2.3 渲染进程内存 —— 39.6 ~ 40.9 MB

**这一条踩过坑，值得记下来。** 原实现写的是
`webContents.getProcessMemoryInfo()` —— **Electron 44 已经把它移除了**
（早期版本有）。现在唯一的路径是：

```ts
const pid = wc.getOSProcessId();                       // 该窗口渲染进程的真实 pid
const metric = app.getAppMetrics().find((m) => m.pid === pid);
const kb = metric.memory.privateBytes ?? metric.memory.workingSetSize;
rendererRssBytes = kb * 1024;                          // ⚠️ 单位是 KB
```

三个细节：

- **必须按 pid 匹配，不能按 `type === 'Tab'` 挑**。多窗口下会有好几个 Tab 类型进程，
  挑第一个等于随机数。
- **`app.getAppMetrics()` 的 `memory` 字段单位是 KB**。不乘 1024 会得到
  "渲染进程占 39.6 KB" 这种荒谬但看起来正常的数字 —— 它不会报错，只会悄悄错。
- `privateBytes` 标了 `@platform win32`，别的平台拿不到，所以退到 `workingSetSize`。
  取 `privateBytes` 是为了排除与其他进程共享的部分 —— 这一项问的是"这个窗口自己占了多少"。
  这也是这个数（约 40 MB）比主进程（约 140 MB）小得多的原因：
  真正吃内存的 Chromium 共享部分不在"私有"里。

### 2.4 流式首 token 延迟 —— 27 ~ 28 ms

来自自检的流式探针（`probe.streamUsage.ttftMs`），不是估计值：
`agent:run` 发出到**第一个 `token` 事件**到达探针订阅点之间的毫秒数。

括号里那个"不含上游"是重要的限定：本项目的 Agent 内核在 M3 阶段是**脚本化运行时**
（`setInterval` 吐字），没有真实 LLM 调用。所以 28ms 量的是
**core 事件流水线 + 跨进程推送 + 背压队列**这一段的自有开销，
不包含任何网络或模型推理时间。换成真实 LLM 后这个数字会由上游主导 ——
届时它衡量的就不再是本项目了。

### 2.5 流式帧率 —— 179 ~ 180 fps

流式期间用 `requestAnimationFrame` 实测：

- **为什么不用 `setInterval(…, 16)` 数次数**：那测的是定时器有没有按时触发，
  与画面有没有真的刷出来是两件事。rAF 的回调频率直接等于浏览器愿意给的帧机会，
  掉帧时它同步下降。这才是"卡不卡"的判据。
- **探针跟着流一起起停**：`'start'` 事件启动，`'done'` / `'error'` 停止并上报。
  中途停会把"半程帧率"当成整段读数；不启停则会在空闲期白测。

**这个数字的解释边界（必须说明）**：rAF 的**上限由显示器刷新率决定**。
180 fps 说明本机是 180 Hz 显示器、且流式期间**一帧没掉** ——
但它**不能拿来跟 60 Hz 机器比**，在 60 Hz 机器上这条指标的天花板就是 60。
所以"≥ 55 fps"这条目标值真正有信息量的部分是：
**实测值顶到了硬件上限**，而不是"比 55 高很多"。

反过来说，这个指标的形状是对的：它测的是"流式渲染有没有把主线程堵死"，
而这件事与刷新率无关 —— 真堵住了，180 Hz 上也会掉到个位数。

### 2.6 Win 安装包体积 —— 98.1 MB

`102,870,585 字节`（`packages/shell-electron/dist/pack/crossdeck-Setup-1.0.0.exe`）。
完整构成与"为什么没走删 DLL 那条路"见 README「已知限制」第 2 条与
`docs/plans/2026-10-04-m4-m6-开发计划.md` §2.3。

未压缩产物实测（`win-unpacked/`，**21 个文件，合计 321.2 MB**）：

| 项 | 未压缩 |
| --- | --- |
| `crossdeck.exe`（Electron 44 运行时主体） | 234.6 MB |
| `dxcompiler.dll`（DirectX Shader Compiler） | 24.6 MB |
| `LICENSES.chromium.html`（法律要求随附） | 19.5 MB |
| `resources.pak` / `icudtl.dat` | 11.9 / 10.4 MB |
| `vk_swiftshader.dll` / `d3dcompiler_47.dll` / `ffmpeg.dll` | 5.3 / 4.5 / 3.0 MB |
| `locales/`（裁到 `en-US` + `zh-CN`） | 1.12 MB |
| **`app.asar`（本项目全部代码）** | **0.93 MB** |

321.2 MB → 98.1 MB（**压缩率 30.5%**），靠 `electronLanguages` 裁 locale +
`compression: maximum`。

> ⚠️ **订正**：`docs/plans/2026-10-04-m4-m6-开发计划.md` §1.3(a) 的括注写"未压缩 369MB"，
> 与本表不符。本表是逐文件实测值，**以本表为准**（369 那个数没有留下量法，
> 且与逐文件统计出来的 321.2 MB 对不上）。

**一句话结论**：安装包体积由上游运行时决定，**自有代码占未压缩产物的 0.29%**。
这是选 Electron 的真实成本，不是本项目没优化。

## 3. 改进项

### 3.1 主进程内存余量只有 3.7%（144.44 / 150 MB）

这是六项里最紧张的一项，而且**它会随功能单调增长**：main 侧现在的常驻物是
会话表、工作区表、路径缓存与 IPC 注册表 —— M4 之后多了 `FsPort` 与 `WorkspaceStore`，
M5 之后多了 `electron-updater` 的检查器。再加一个后台任务就顶线了。

候选手段（按"性价比"排序，尚未实施）：

1. **窗口关闭后主动丢缓存**。`WorkspaceStore` 与路径 realpath 缓存按窗口持有，
   窗口销毁时释放 —— 多窗口场景下这是线性增长的那一项。
2. **`app.getAppMetrics()` 的窗口级归因**。现在只报总数，分不出"哪一部分是
   main 自己的、哪一部分是 Chromium 的"。没有归因就只能猜。
3. **把阈值从 150 MB 上修**。但这是最后手段：**先量清楚再谈改口径**，
   否则就变成了"为了数字好看而调整标尺"。

暂不实施的原因：当前**达标**，且优化点（多窗口缓存释放）要等 M6-3 的多窗口形态
定下来才谈得上 —— 现在改是凭想象优化。

### 3.2 安装包余量只有 1.9%（98.1 / 100 MB）

`< 90MB` 的原始口径已在 M5-1 修订为 `< 100MB`（修订理由与逐项构成见 §2.6）。
唯一能过 90MB 的手段是删 `dxcompiler.dll` + `dxil.dll`（−19.8 MB → 约 78 MB），
**已评估并否决**：那是 WebGPU / Shader Model 6 的着色器编译路径，
本机 GPU 路径根本起不来，删了无从验证 —— 不拿真实用户去赌一个数字。

### 3.3 性能采样没有记录「测量条件」（§2.1 的方差来自这里）

`PerfSnapshot` 现在只有四个数字，没有"这是在什么条件下测的"。
于是同一条命令能给出 316 ms 和 935 ms，而报告里只能人工解释一段。

三条候选做法，按顺序做：

1. **报告里带上"本次是否为进程首次运行"**（`perf.ts` 加一个 `isFirstRun` 之类的字段），
   或者更直接：**同时上报页缓存状态**（Windows 上可读
   `GetProcessMemoryInfo` 之外的信息有限，但至少可以上报"这是第几次采样"）。
2. **多次采样取中位数而不是单次值**。`perf:sample` 改成可重复调用，
   报告里给 `median` 与 `p95`，而不是一个孤零零的数。
3. **把冷启动拆成两段**：`进程启动 → main ready` 与 `main ready → 首帧`。
   前者是 Electron 的运行时代价（我们改不了），后者才是**我们自己代码**的启动开销
   —— 现在这两个混在一个数字里，优化时无从下手。

这一条比 3.1 / 3.2 更值得先做：它不影响判定结果，但**决定了这个数字能不能被信任**。

## 4. 口径与已知弱点

一份性能报告的诚实度取决于它敢不敢写自己的测不准之处。

1. **帧率的采样窗口 = 一次流式的持续时长**，本机约 0.7 s（约 120 帧）。
   样本量够用，但**短窗口对偶发抖帧不敏感** —— 一次 20 ms 的卡顿在 0.7 s 里
   只把均值拉低 3%，会被四舍五入吃掉。
   若要更严格，应该上报采样**窗口时长**并同时记录 **p95 帧间隔**（不只均值）。
   本次未做，因为 §2.5 的目标（"流式有没有堵死主线程"）用均值已能判定。
2. **冷启动的终点是渲染层的自报**。如果渲染层因为异常根本没报，
   `coldStartMs` 会是 `0` —— 脚本把它当"没测到"处理、推一条 warning 进报告，
   **而不是当成 0 ms 的优异成绩**。这条区分在 `readPerfSnapshot()` 里是显式的：
   ```ts
   coldStartMs: firstPaintAt === 0 ? 0 : firstPaintAt - BOOT_AT,
   ```
3. **六项里有两项（帧率、首 token）依赖自检的脚本化 Agent**。
   换成真实 LLM 后首 token 由上游主导，本项目的自有开销要从 `totalMs − ttftMs`
   之类的差分里才看得出来。届时这两项的口径需要一起重新定义。
4. **只有 Windows 数据**。mac / linux 产物不存在（见 README「已知限制」第 3 条），
   也就没有对应性能数字。与其估一个，不如空着。
5. **安装包体积没有随时间维度的样本**。它是个"构建产物属性"，不是运行时指标 ——
   98.1 MB 是当前这一次打包的结果，改一次依赖就可能变。它在这一节里
   更像是"版本快照"而非"性能指标"，放在同一张表里只是为了完整性。
